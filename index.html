A sound discovery — and a migration that must compound, not carry the debt across

Six function-level future-state designs are individually strong. But this is not a greenfield build — it is the migration of an 18-year-old Salesforce org, still anchored in Salesforce Classic, onto Education Cloud. The value sits in the seams between the functions; the risk sits in the debt the legacy org carries across — which is exactly where a migration either compounds or quietly re-creates the integration debt the platform was meant to retire. The path forward is to treat the next phase as one architecture, on the foundation MyCC is already building, and close the seams before the build begins.

Situation
The Education Cloud discovery is complete across six functions and each future-state design is sound — but the work ahead is a migration off an 18-year-old, Classic-era org onto a modern platform. A once-in-a-decade lift.
Complication
The value is trapped at the seams between functions — an ~8% closed-enrol-to-first-day loss, 600–700 payments reconciled by hand weekly, frequent minor-error compliance rejections. Migrate function-by-function and the build inherits each seam as a defect and carries 18 years of integration debt across with it.
Question
How does MyCC turn a strong discovery into a migration that compounds value — rather than re-creating, on a new platform, the very debt it set out to retire?
Answer
Treat it as one architecture on the single data foundation MyCC is already standing up: close six seams in a short pre-kickoff window, migrate onto the foundation rather than the legacy systems, then build revenue-first across two phases — the revenue-bearing functions live for a December go-live, the full constituent journey by February — arranged so the work compounds.

What the path forward asks of leadership

Four points to align on
1. Close the seams first. Resolve the six seam-closing definitions in the selection-to-kickoff window, before Sprint 1, so no function build ships against an open seam.
2. Name the owners. Assign a single accountable owner to each of the six artefacts, per the governance & decision-rights view.
3. Migrate onto the foundation, not the legacy systems. Land Education Cloud on the shared data foundation MyCC is already building, so it inherits one identity model and one metric set rather than a second generation of integration debt — the whole-system picture is in the whole-system view.
4. Decide what carries forward. A clean migration is as much about what MyCC leaves behind as what it brings — settle the data-preservation rules (transcripts, student records, audit history) before migration design, not during it.

Read together, the discovery describes one observation

The current-state work and the six future-state designs describe a capable institution whose friction sits not inside any one function but at the seams between them. Each design makes its own function measurably better. Read across one another, they reveal where one function’s assumption quietly becomes another’s break: the active-student trigger carries a different definition in five functions; the Skills object appears in Education and as a matching surface in Career Services without a shared schema; Salesforce is the system of record in five designs and explicitly is not one in Finance; Compliance was designed in isolation, so its audit overlay still has to be read across the other five; and Alumni — a six-person team against hundreds of graduates a month — owns a handoff that no system event defines. The systems are sound. The connective tissue is the work.

The thesis — one architecture, seams treated as first-class

The next phase is not six functional rollouts. It is one architecture: a data foundation that holds identity, the active-student trigger and the certified metric set; an action surface where Salesforce, Education Cloud, Tableau Next and Agentforce run the work; an integration layer where Workato, the Baker Tilly PHP bridge to Sage Intacct, the Canvas SFTP feed and the Data 360 connector into the Data Lake run on declared cadences; and an end-user layer where students, advisors, instructors, compliance officers, finance staff and alumni-services staff act. The six function designs are the right shape for each function. What they do not yet draw is the connective layer — which system owns which field, which trigger fires on which event, which definition is shared and which is local. That layer is the seam set, and the order in which the build closes it decides whether it closes cleanly or hardens into the next generation of friction. Agentforce is not a fourth product; it is what becomes possible once the foundation and the seam set are in place — and what compounds advisor load if it sits in front of students before they are.

One system, not a module — why getting this migration right is a whole-system problem

The recommendation to move MyCC onto Education Cloud was MLVeda’s own — set out in the January platform strategy, after an objective assessment of an org approaching two decades old weighed against MyCC’s goal of durable revenue growth without proportionally adding headcount. Read Education Cloud in isolation and the migration inherits the seams and carries that debt across. Read it as one component of the whole system — foundation, analytics, agents, and the legacy org it leaves behind — and the six function designs resolve into one operating layer that compounds.

01 The Operating Model & Its Seams

Six functions, one model — and the seams that connect them

A two-beat read for each function: what current-state surfaced, what the future-state design proposes, and the seam the pair leaves open. The function blocks describe what good looks like inside each function. The Seam Ledger is what reading the six together reveals — and what the deliverables close.

1.1  Education High
Current state
  • Student journey runs across disconnected surfaces (LMS, attendance, advising); a longitudinal view needs manual joins.
  • A 2010 spreadsheet still drives much of the course calendar; the Comptia voucher cycle is a high-variance manual touch.
  • An 8% closed-enrol-to-first-day gap has no single owner; survey instrumentation is reactive.
Future-state design
  • A unified student portal (Experience Cloud) carrying point-in-time history and a course-level Student Status field.
  • A Skills & micro-credentials object linked to Course, Student, Instructor — intended to feed Career Services.
  • AI voucher agent against the Comptia API; Zoom-API attendance capture; a Student Promise field and threshold-routed surveys.
Seam left openThe Skills object is right for Education but not yet aligned to the Career Services matching surface — the two designs share a name without a definition. Resolved in Seam 02 and authored in D1.
1.2  Enrollment High
Current state
  • ~150 daily contact-centre touches, ~70 hot transfers inside that volume; lead carryover into the application surface is partly manual.
  • Group consultations add wait time and uneven student-advisor matching.
  • Three legacy tools (Five9, Mowgli, Sumo) overlap on the front end; EVA document validation lands late, when re-collection cost peaks.
Future-state design
  • Lead-to-Opportunity carryover automation with lead scoring and best-to-best advisor routing; hot-transfer round-robin replaces group consults.
  • The Education Cloud Application object becomes the central enrollment hub; a unified portal restores funnel status visibility.
  • FA file-queue prioritisation, EVA validation moved earlier, contact-centre consolidation retires the three legacy tools.
Seam left openThe design assumes Agentforce in front of students will deflect volume previous self-service did not — without naming what is different this time. The adoption question is not a feature question. See Seam 05, governed in D5.
1.3  Career Services High
Current state
  • A representative advisor reports ~6 placements per month; new advisors ramp behind tenured ones, with caseload reassigned at 90 days.
  • The Employer Verification Form is fully manual — no DocuSign pre-fill, no 30-day-gate trigger.
  • “Employment in field” carries different working definitions across advisors, propagating into ASSET reporting; employer conversation tracking is informal.
Future-state design
  • AI ingestion of phone/text transcripts into a structured employer-conversation record; a placement-readiness score with drift alerts.
  • A geo-targeted job board, a student career portal, AI job-matching against a skills surface, an employer-verification portal and a structured EVF workflow.
  • Advisor load-balancing, a 90-day unplaced auto-reassign, and a cross-functional “Success Team” holding attribution across enrollment, education and placement.
Seam left openThe readiness score and AI matching both rest on a skills schema Education owns elsewhere; “employment in field” needs a Compliance-grade definition before it can be a metric. See Seam 02 (D1).
1.4  Finance High
Current state
  • 600–700 weekly student payments processed manually; the Regent→Sage Intacct Title IV transfer is partly manual.
  • Loan-servicer tracking (incl. Paramount) sits in informal logs; remittance allocation has no integrated workflow and reconciliation is approximated weekly.
  • Withdrawal cascades (LOA, transfer, midpoint) do not propagate cleanly; Finance states plainly that Salesforce is not a financial system of record because the values never reconciled.
Future-state design
  • An automated Regent→Intacct Title IV flow; structured loan-servicer tracking in Salesforce.
  • Integrated remittance automation with real-time aging in Intacct; a Salesforce ↔ Intacct financial-data-integrity bridge.
  • A student financial self-service portal; cohort-level withdrawal and revenue analytics with enrollment-driven forecasting.
Seam left openThe design preserves Finance’s stated position that Salesforce is not the system of record — while five other designs treat it as one. The connective layer is a field-by-field data-authority matrix. See Seam 03, authored in D1.
1.5  Compliance High
Current state
  • Manual file review yields frequent minor-error rejections and resubmission cycles; the EVA AI tool is hard-coded to block files on any gap, and may not survive migration intact.
  • Paramount has no integration — manual download, manual upload. Post-close-enrol changes (LOA, transfer, midpoint) do not propagate to Finance/Intacct.
  • Reporting footprint spans IPEDS, ASSET 28.1, TWC and VA; Texas TWC still carries archaic manual sign-off.
Future-state design
  • Structured workflows for five triggers — transfers, LOA, withdrawal/R2T4, retakes, document validation — each with routing, status field and SLA clock.
  • Validation moves earlier; Paramount/EVA/DocuSign collaborate against a single document object; automated R2T4 fires on withdrawal so Finance and Title IV read one calculation.
  • An immutable native audit record per event, with history extended via Field Audit Trail beyond the ~18-month field-history cap and a defined retention and archive path — transcript generation rationalised off the Conga managed package.
Seam left openThe design was held in isolation. Its five triggers each intersect a move in another function, and the other five designs have no single audit pass against ED, ASSET, FERPA, VA and TWC. The cross-function overlay is the discrete artefact. See Seam 04 (D5).
1.6  Alumni High
Current state
  • A six-person team handles hundreds of graduates per month; outreach is spreadsheet-segmented, so dormant and recent graduates share one cadence.
  • VA cohort logic is local knowledge: funding year resets Aug 1, the re-enrolment window is ~5.5 months, and a student cannot repeat the same program — none of it sits in the data layer.
  • Paramount loan-status lookups run manually, file by file; the graduate record is fragmented across Salesforce, the LMS exit record and placement history; the Career Services handoff is informal.
Future-state design
  • An Alumni object carrying cohort, VA window, employment status, last placement and refinancing eligibility — populated from Education, Career Services, Compliance and Paramount.
  • Trigger-based segmentation (5.5-month VA window, 90-day post-placement check-in, dormancy thresholds) and a defined Career Services→Alumni handoff with a status-change trigger.
  • Paramount loan-status surfaced automatically; a re-enrolment intent score visible to Alumni and Enrollment so a returning alumnus is not a new lead.
Seam left openAlumni sits at the end of three flows (graduation, placement-verified, record closure) and the start of one (re-enrolment). The handoff cadence and the Career Services/Alumni data-ownership question is the sixth seam. See Seam 06 (D3, D6).

1.7  Integration Architecture — the layer the six designs run on

Named connectors and cadences High
What discovery named
  • Canvas→Salesforce via daily SFTP flat files (25K–38K rows); reconciliation is manual when a file is partial.
  • Regent via Workato XML on a 30-minute cadence — the most real-time inbound feed. Sage Intacct via a Baker Tilly PHP daily batch, so mid-day events wait until next day.
  • Data 360 connects SF→Data Lake; Five9 via Listing Plus; Zoom runs without SSO and without a SF integration. Data 360 is positioned as metadata middleware, not a warehouse.
What the layer must hold
  • A named cadence register, signed by the consuming owners — R2T4, LOA and withdrawal cannot wait for the next-day Intacct batch.
  • Middleware to lift Sage and Zoom onto event-driven cadences alongside Regent; a Zoom↔LMS attendance reconciliation that closes the no-SSO gap first.
  • An explicit Data 360-vs-Data Lake position, with aggregate analytics resolving to the Data Lake and Tableau Next.
Why it mattersFour of the open seams are seams between systems as much as between functions. Naming the cadence and middleware path turns them from observations into engineered surfaces. Authored in full in D4.

1.8  Security & Change Management — the posture the next phase runs on

Identity, permissions, retention, adoption Medium-High
Current state
  • MFA via Salesforce Authenticator + Google Authenticator; failure modes at the edges (contractor access, service accounts).
  • Permissions are profile-based; the intent is permission-set groups, but the current-to-future mapping is undrawn. Data Shield is in place but underbuilt.
  • Field-history tracking is capped at ~18 months and a fixed field count (already maxed out); records are neither archived nor purged today and no formal retention policy is set; change management is real but informal; Conga Composer generates transcripts but its lifecycle is undocumented.
Future-state design
  • A permission-set-group blueprint mapping each function to a group with delegated admin; a Data Shield expansion following the Compliance sensitivity map.
  • A formal retention lifecycle — audit history extended beyond the ~18-month field-history cap via Field Audit Trail, a defined retention policy and archive target, documented retrieval — with the native audit trail as the canonical compliance artefact.
  • A named change-champion per function and a residual-risk register that captures adoption function by function.
Why it mattersPermission model and retention are usually run-time concerns; here both are design-time. The blueprint decides who can act in each surface; retention decides whether Compliance has a defensible trail on day one; change management decides whether the Agentforce seam closes or compounds. Authored in D5.

03 Sequencing

From seam-closure to kickoff — the window, then a revenue-first build in two phases

A short definitional window sits between vendor selection and kickoff: six seam-closing artefacts produced before the build begins. Then the build runs across a July–February calendar in two phases, sequenced revenue-first. Phase 1 stands up the foundation and the revenue-bearing functions — Enrollment and Marketing, then Finance and Compliance — targeting a December revenue go-live (the stretch the pod drives toward). Phase 2 completes the constituent journey — Education, Career Services and Alumni — for the committed February full go-live. The order is deliberate: the functions that carry revenue and compliance exposure go first, so value lands before the academic-year surfaces. Define the seams, then sequence the surfaces.

Why revenue-first, and why two phases
The calendar is not arbitrary. Phase 1 puts the foundation, enrollment and the financial/compliance spine into production for a December revenue go-live — the highest-value, highest-exposure surfaces first. Phase 2 lands the education, career-services and alumni journey for the committed February full go-live. The sequence respects three hard calendar facts: a roughly two-week December operating shutdown (no go-live lands inside it), a January go-live freeze, and platform-licensing timing — full Education Cloud SKU access in November, new-org licensing from late January, with the existing org held as a buffer through late February. MLVeda drives hard for the December date; the February commitment is the one MyCC can plan against without absorbing the schedule risk.

The migration underneath the sequence
Every sprint above runs on one fact the function designs do not state: this is a migration off an 18-year-old Salesforce Classic org, not a greenfield build. The Sage Intacct integration still runs on the Classic-only API; eighteen years of records, attendance and transcripts sit behind it. Two decisions gate a clean cut-over and belong in the window, not in migration design: carry-vs-leave — bring only what the future operating model and the record-retention rules require, leaving the rest in a searchable archive — and data preservation — a tested path that reproduces any historical transcript or audit record on demand, owned by a process, not a person. Migrate onto the foundation rather than the legacy systems and the debt stays behind instead of crossing the boundary (R13).

The platform view — what Sprint 1 lands on

Five layers move from the source systems, through the foundation that resolves identity and certifies metrics, into the surfaces operators use — with a side-feeding intelligence layer that acts on the foundation rather than the source systems. Layer 3 carries an explicit internal split: Data 360 is metadata middleware (identity, metric definitions, routing); the Data Lake is the analytics warehouse. The two are not interchangeable, and D1’s matrix names which one wins per field.

Layer 3 is built first: every downstream surface and intelligence function is faster to deliver and cheaper to maintain when it inherits one identity model and one metric definition. Education Cloud, when it lands, connects into Layer 3 rather than the source systems — avoiding a second round of integration debt. Full architecture in D4.

  • Where records actually land for analytics; carries audit lineage and certified-metric reads.

E · The delivery model — a forward-deployed pod

The program is delivered by a lean, senior, forward-deployed pod — not a coordination pyramid. A forward-deployed engineer is embedded in MyCC’s systems and daily cadence: remote, but deployed into the operating reality, with onsite anchor moments at the seam-closing window, each sprint demo, and go-live. The people who understand the domain are the people who build it — so there is no spec-to-offshore hand-off, the gap where a function-by-function build loses the active-student and data-authority dependency. And the pod carries whole-system context from day one, because it already runs the Data 360 foundation this build lands on.

The pod is lean and senior-dense — a forward-deployed lead architect and Education Cloud engineers carrying the build, with fractional delivery/change-management and QA/UAT loading — front-loaded so the foundation and the revenue-bearing functions reach the December revenue go-live and the full constituent journey lands by the committed February go-live. The shape is deliberately senior-dense: more hands-on build capacity and far less coordination overhead than a conventional onshore-analysis-plus-offshore-build team — and it is the shape the SoW resources and prices. This document carries no headcount, hours or cost figures; those live in the SoW. Months are illustrative against the calendar constraints; exit is governed by seam-closure (R6, R14).

F · What this asks of MyCC

The same model defines what the program asks of MyCC’s own people — and the answer is deliberately bounded. C · Identity, access & sharing model

The portal’s risk is not its look — it is who can see which record. The model is declarative and audited end to end, and it inherits the Phase 1 permission-set-group blueprint (D5) rather than inventing a parallel access scheme.

Identity

Sharing

Audit
Document uploads and employer EVF submissions land as Cases with a logged audit row; Field Audit Trail (D5) extends portal-triggered history beyond the ~18-month cap. Every portal write is a request against a workflow, never a direct write to a system of record.
